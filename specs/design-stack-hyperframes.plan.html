¶ Summary

The shared design stack gains HyperFrames, the Apache-2.0 HTML-to-MP4 motion framework, as a fifth verified source beside Taste, Impeccable, the design references and img2threejs. Its 21 published agent skills appear in the catalog as tools under hyperframes:<skill>, a small guard opts a task into video work the way the 3D guard does, and an install that predates this source keeps working offline until the owner runs an explicit update. HyperFrames is a capability a project can use, never a visual direction a brief is written for.

Behavior

design_stack.py setup and update stage HyperFrames from its official Git repository into the verified release at sources/hyperframes/, record its revision in the manifest beside the other four, and promote it atomically with them. No installer runs for it: its skills are read in place, the same way the design references and img2threejs are.

design_stack.py catalog lists one tool entry per HyperFrames skill found at sources/hyperframes/skills/*/SKILL.md, with the ID hyperframes:<dirname>, the frontmatter name as its title and the frontmatter description as its fit text. The router skill hyperframes:hyperframes is required for the source to validate; every other skill is discovered, so a new upstream skill appears without changing a count in the adapter.

design_stack.py select and brief refuse a hyperframes: ID as the primary direction or as a reference, exactly as they refuse impeccable: and three: IDs today.

A new guard, scripts/hyperframes.py, answers two questions the skill text asks agents to settle before touching video: whether the task opts into HyperFrames (an explicit request in the task for a video, an MP4, motion graphics or an explainer video, or a Motion rule that names HyperFrames; never a bare render, which ordinary UI tasks use, and never a Motion rule that only mentions an existing video element), and whether a render is production or still a prototype (the composition passes hyperframes check and an MP4 was rendered). It also reads the pinned CLI version from the release's packages/cli/package.json, so an agent runs npx hyperframes@<that version> and never a floating latest.

A manifest written before this source exists stays valid: status, catalog, select, brief and refresh run offline against it, the catalog simply has no hyperframes: entries, and status names the source an update would add.

Inputs

  • The official repository https://github.com/heygen-com/hyperframes.git, overridable through DESIGN_STACK_HYPERFRAMES_URL like every other source.
  • The release layout: sources/hyperframes/skills/<name>/SKILL.md with YAML frontmatter name and description; sources/hyperframes/packages/cli/package.json with a version field.
  • A task description and the project brief's Motion section, for the guard.
  • The existing manifest, which may list four or five sources.

Outputs

  • Manifest sources carries a hyperframes revision after setup or update.
  • Catalog entries {"id": "hyperframes:<name>", "kind": "tool", "title", "fit", "source_revision", "path"}, one per installed skill.
  • hyperframes.py returns should_run_hyperframes(task, brief_motion) as a boolean, production_status(gates) as {"label", "open_gates"} with the required gates check and render, and cli_version(release) as the pinned version string.
  • status on a four-source manifest prints Ready <id> (offline; update adds: hyperframes).
  • /design-stack SKILL.md documents the source path, the opt-in rule, the pinned-version rule and the prototype label; /build names the video guard beside the 3D guard; the README skills table row follows the new description.

Edge Cases

  • HyperFrames stores regression baselines in Git LFS. The clone runs shallow (--depth 1) with GIT_LFS_SKIP_SMUDGE=1, so setup never downloads baselines; the other four sources keep their full clones.
  • A skills/<name>/SKILL.md without a frontmatter name uses the directory name as its title; a missing description yields an empty fit.
  • A release whose sources/hyperframes lacks the router skill fails validation with the existing catalog path is missing or leaves the verified release error, so a broken upstream never promotes.
  • A manifest listing a source the adapter does not know is still an error (unsupported design-stack manifest); only a missing known source is tolerated.
  • update on a four-source manifest always stages all five sources; the revision comparison treats the missing key as changed, so the installers run and the new release carries five revisions.
  • The task text "no video" or "remove the video" does not opt in; a Motion rule that only describes UI easing, or that mentions a video element without naming HyperFrames, does not opt in; "fix the re-render flicker" does not opt in.
  • hyperframes.py never runs the CLI or touches the network; the production gates are facts the agent records after running hyperframes check and hyperframes render itself.
