¶ Summary

jplugin gains /diagram, a thin skill that turns a system, flow, schema or history into a checked, explorable standalone HTML diagram through Archify. Archify is installed once in user scope as a pinned tool, never as a skill the harness can route to, so /diagram is the only diagram entry point and the drawing instructions stay upstream's. Diagrams of a real codebase always carry source citations verified against the pinned commit. The homegrown flow/sequence DSL keeps drawing inline spec fences; Archify draws the standalone diagrams. The one decision not to miss: Node is a hard requirement for /diagram, a browser is not.

Behavior

A user types /diagram <what> (or a phrase such as "draw the architecture", "visualize the request flow", "map the module tree", "archify this"). The skill:

  1. Locates the installed tool at $ARCHIFY_HOME (default ~/.local/share/jplugin/archify). When it is absent, it prints the one-line install command and stops. When node is absent or older than 18, it says so and stops. Neither case produces a diagram or falls back to another renderer.
  2. Reads upstream's authoring instructions from the install directory (<home>/archify/SKILL.md and the references it names) and follows them for type selection, candidate authoring and finalize. All ten diagram types are available; Archify's own type router picks.
  3. Adds jplugin's conventions on top of upstream's:
    • Evidence is mandatory for a codebase. When the subject is a repository, the candidate pins meta.repository to the clean HEAD of that repository and every component carries sources; finalize runs with --repo-root. A described system (no repository) is authored freehand.
    • Output location. A system or architecture diagram lands at docs/architecture/<slug>.html beside its candidate docs/architecture/<slug>.architecture.json (or <slug>.<type>.json), regenerated in place. A diagram that illustrates a spec lands beside it as specs/<feature>.<type>.html. Archify's working folder .archify/ is gitignored and holds receipts and captures only.
    • Browser resolution. Before finalize, the skill sets ARCHIFY_CHROME to the first of: an existing ARCHIFY_CHROME, a Chrome or Chromium on PATH, the Chromium that playwright-cli installed. When none is found it runs the non-browser gates (validate, deliver, check) and states in its reply that browser evidence did not run.
    • Diagrams only. Archify's explainer mode is not exposed; a request for "a page" routes to /html-presentation as today.
  4. /diagram --refresh <path> re-authors an existing committed candidate against the current HEAD: it re-reads the cited source, updates components, citations and the pinned revision, and re-runs finalize. Staleness is detected only through this command; /wrap-up-session leaves diagrams alone.
  5. The reply follows Archify's output contract: a clickable link to the HTML, one or two sentences of takeaway for a codebase diagram, and anything that changes how the diagram should be read. It never claims visual review that did not happen.

Three existing skills gain a diagram moment:

  • /how ends every answer with one line offering a diagram of the flow it just explained; nothing renders until the user says yes. Its explainer prompt stops suggesting Mermaid or ASCII diagrams in chat.
  • /plan offers a diagram in one line after the spec is written, when the feature spans more than one component.
  • /system-design-planning produces an architecture diagram beside its spec as part of its deliverable when the tool is installed, and prints the install command (without stopping) when it is not. Its flow and sequence fences are unchanged.

Installation and provenance:

  • install.sh gains a section after the Playwright one: when node ≥ 18 is present it clones Archify at the pinned tag into $ARCHIFY_HOME, verifying the checked-out commit equals the pinned commit; when the directory already holds that commit it reports "present"; otherwise it prints a NOTE with the install command and continues. Nothing prompts and the exit code never changes.
  • .github/upstreams.json gains an entry of kind: "installed" for Archify: url, ref: refs/tags/v3.2.0, baseline = the tag's commit, no paths, source_notice. scripts/check-upstream-drift.py accepts the new kind (paths forbidden, ref may be a tag) and reports drift for it the same way. Sources without kind keep today's vendored semantics.
  • THIRD_PARTY_NOTICES.md gains an "Archify (installed tool)" section with the MIT notice; README's Sources section names it.
  • /tidy gains a tenth check, tools, that compares the commit checked out in $ARCHIFY_HOME with the registry's pinned baseline. No install on this machine → inconclusive with the note; a different commit → Tier 1 with the re-install command printed, never applied.

Inputs

  • /diagram <free-text subject> — a described system, or a request about the current repository (or another path the user names).
  • /diagram --refresh <candidate.json | diagram.html> — an existing committed candidate.
  • Environment: ARCHIFY_HOME (install root override), ARCHIFY_CHROME (browser override), node on PATH.
  • Upstream: https://github.com/tt-a1i/archify at tag v3.2.0, commit 208acba8d412335185b2056fedf54b3405df43fb.

Outputs

  • A standalone HTML diagram and its candidate JSON at the paths above; Archify's receipts under .archify/.
  • A chat reply per Archify's output contract, with the browser-evidence gap stated when it applies.
  • install.sh: a cloned, pinned Archify under $ARCHIFY_HOME, or a NOTE.
  • Drift job summary: a drift: line for Archify when upstream's tag moves ahead of the baseline.
  • /tidy report: a tools row.

Edge Cases

  • Tool absent → the install command is printed and /diagram stops. No DSL or html-presentation fallback, silent or otherwise.
  • node absent or < 18 → stated and stopped, with the Node requirement named.
  • No browser → non-browser gates run; the reply says "automated checks passed without browser evidence". The diagram is still delivered.
  • finalize fails → the skill follows upstream's repair contract (edit the connected neighbourhood, re-run with a new --out-dir), never claims success on a non-zero exit, and reports the failing gate when repair is exhausted.
  • Dirty worktree when diagramming a codebase → the candidate still pins HEAD; the reply names the changed paths, and no uncommitted bytes are cited as evidence (upstream's rule).
  • --refresh on a candidate whose cited component no longer exists → the component is removed or re-anchored from a fresh read of the source; the reply names what was dropped or merged.
  • A request for "a page" or "an explainer" → not /diagram; routes to /html-presentation.
  • /system-design-planning without the tool → the spec and its DSL diagrams are produced as today, plus one install-command line; the session does not stop.
  • Pi and Codex sessions never ran install.sh → the printed install command is the only path; /diagram is otherwise harness-neutral (Node CLI, no Claude Code specifics).
  • An upstreams.json entry of kind: installed with paths → the validator rejects it, naming the field.
  • $ARCHIFY_HOME holds a commit other than the baseline → /tidy tools Tier 1 finding; install.sh re-clones only when told to, never on its own.
