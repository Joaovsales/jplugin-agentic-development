One tree, one namespace, one name

Claude Code users of this workflow read skills from .claude/skills/, a byte-identical copy of the canonical .agents/skills/ tree that a convention, an allowlist and tests/test-skill-parity.sh keep aligned; installed copies are already drifting (~/.claude/skills/ still carries deslop, simplify, tdd and verify-e2e, which the repository no longer ships). This change ships the repository as a Claude Code plugin named jplugin whose manifest points at .agents/skills/, declares that plugin in the one settings file /sync already delivers to every project, removes the template's .claude/skills/ copy, adopts the repository's current identity jplugin-agentic-development wherever the old name still appears, and retires the compatibility shims that only existed for the two-tree layout or for projects synced before earlier renames.

Out of scope: moving agents or hooks into the plugin, renaming any skill, project-local skills a project writes into its own .claude/skills/ (verify-<app> stays as it is), and the Pi and Codex install paths, which read ~/.agents/skills/ and do not change.

Two pinning models exist today. Claude Code is project-pinned (the project's .claude/skills/ shadows ~/.claude/skills/). Pi and Codex are machine-pinned (~/.agents/skills/ prose, project-relative scripts). This spec keeps Claude Code project-pinned, which rules out a machine-level plugin as the only delivery path.

Verified outside the repo (Claude Code 2.1.227): plugin skills are always namespaced /plugin:skill; plugin.json skills accepts a ./-relative path and adds to the default scan; a marketplace added from a local directory with source: "./" loads in place; project .claude/agents override plugin agents; enabledPlugins is honoured from project settings; Claude Code never scans .agents/skills.

Arrows (2) and (3) are two writes to ~/.claude/plugins/; a crash between them is recovered by idempotency on the next run, so no transaction is needed.

Marketplace-name collision (spike question S3). A developer machine holds the directory-source marketplace from install.sh; a downstream project's settings.json declares a github-source marketplace. If both must share the name jplugin-agentic-development, Claude Code's behaviour on the second registration is unverified. Slice 1 answers it; the fallback is a second marketplace name for the directory source (jplugin-agentic-development-dev) with the plugin enabled from exactly one of them per machine.

Failure unit. A broken manifest stops every jplugin: skill for Claude Code users and nothing else — Pi and Codex never read it. A refused retirement guard stops /sync Step 6 for that project only; the checkout step has landed and the project still has both /name and /jplugin:name. A failed plugin install leaves the machine on its previous state, because step 4 never runs after a failed or skipped install. A declined marketplace prompt on a fresh clone leaves that clone without jplugin: skills; the banner line in (6)–(7) is the only signal, and it is loud on purpose. Removing the legacy migrations from /sync stops nothing: a project that still carries .claude/commands/ or a ## Deployment Targets section in CLAUDE.md keeps them, and the tooling simply no longer looks there.

Component contracts — can the caller ignore a case it must handle

.claude-plugin/plugin.json (Claude Code reads)

{
  "name": "jplugin",
  "version": "1.0.0",
  "description": "Spec → plan → TDD build → review → wrap-up workflow skills for coding agents.",
  "author": { "name": "jplugin-agentic-development maintainers" },
  "repository": "https://github.com/Joaovsales/jplugin-agentic-development",
  "license": "MIT",
  "skills": "./.agents/skills"
}
  • Outcomes: Claude Code registers every SKILL.md under the path as jplugin:<name>, typed /jplugin:<name>
  • Invariants: no commands, agents or hooks key; name equals plugins[0].name in marketplace.json; version is semver
  • Versioning: version bumps per release; a github install at a pinned ref ignores it; a directory marketplace loads in place

.claude-plugin/marketplace.json (Claude Code reads)

{
  "name": "jplugin-agentic-development",
  "owner": { "name": "jplugin-agentic-development maintainers" },
  "plugins": [ { "name": "jplugin", "source": "./", "description": "…" } ]
}
  • Outcomes: added from a local directory → loads in place; added from GitHub at a ref → copied to ~/.claude/plugins/cache/
  • Invariants: exactly one plugin entry; its name equals plugin.json name; the marketplace name is the install-id suffix jplugin@jplugin-agentic-development and never changes

.claude/settings.json — plugin declaration (synced to every project)

{
  "extraKnownMarketplaces": {
    "jplugin-agentic-development": {
      "source": { "source": "github", "repo": "Joaovsales/jplugin-agentic-development", "ref": "<sha /sync checked out>" }
    }
  },
  "enabledPlugins": { "jplugin@jplugin-agentic-development": true }
}
  • Inputs: ref is the template commit /sync Step 5 checked out; the template repo itself omits it
  • Outcomes: Claude Code offers the marketplace on first open of a clone and enables the plugin; sync-retire.py reads enabledPlugins as its guard
  • Invariants: the existing hooks and env blocks are untouched — /sync merges these two keys (existing merge rule, sync/SKILL.md:601)
  • Idempotency: /sync rewrites ref to the checked-out sha on every run
  • Versioning: whether ref is honoured for github marketplace sources is spike question S4; the fallback is no ref (pinned at install time), recorded in Decisions if it lands

Illegal states

  • retirement of .claude/skills/** committed in a project whose settings.json does not enable the plugin — require_project_plugin refuses before the plan is returned
  • a retired-root file deleted that template history never carried (a project-local skill) — retired_root_candidates intersects with history by construction
  • plugin state with install.sh still copying to ~/.claude/skills/ — step 2 is deleted, not conditional
  • a never-carried ~/.claude/skills/ entry deleted by install.sh — the candidate predicate is current ∪ retired template names; the old "not in the template" set is exactly what is protected

  • the old repository name reappearing in a tracked file — tests/test-repo-identity.sh
  • two marketplaces named jplugin-agentic-development with different sources on one machine — unverified; spike question S3 decides whether the CLI refuses it or the fallback name is needed

Migration and compatibility. Forward: slice 1 proves routing with the fallback removed before anything is deleted; slice 2 renames the repository identity so every later slice pins the new name; slice 5 lands the settings declaration and the retired-root logic while the template still ships .claude/skills/, so a project that syncs between slices 5 and 6 gains the declaration and retires nothing; slice 6 deletes the copy, and the next /sync retires the downstream files under the guard; slice 7 removes the legacy shims, which no live path depends on. A machine re-running install.sh from any commit in between is in both at worst, never skill-less. Reverse: git revert restores .claude/skills/, the old settings.json and the old name; claude plugin uninstall plus marketplace remove clear the machine; a downstream /sync against the previous ref checks .claude/skills/ back out. Until a project's next /sync, both /plan and /jplugin:plan resolve there — noisy, not broken.
