¶ Summary

The perf lane gets two modes, both run by one new skill, /perf. Audit is proactive: it inventories an app's critical paths, measures each with noise control, estimates how fast each should be, reviews the hot paths for wasted work, and writes a ranked report that files one task per finding. Debug is the existing reactive loop, now carrying an expected number beside the baseline and the after, and refusing to call a change inside the noise an improvement. The decision not to miss: a number is only a measurement when it is N runs of one repeatable command, summarised as min, median and spread — every script refuses anything less.

Behavior

Mode selection

/go routes a goal to the perf lane on either kind of cue. The lane's step 1 picks the mode from the goal's words:

  • Audit — the goal asks to audit performance, asks how fast an app or flow is, or names a whole app or flow with no symptom ("audit the performance of the shop", "how fast is this app").
  • Debug — the goal reports one slow path ("checkout is slow", "the export takes 40 seconds", latency, memory, a profile attached).

A goal asking how fast something is goes to perf (Audit), not investigate: its answer is a measurement, not a cited read of the code.

Audit mode (/perf audit <target>)

  1. Inventory the critical paths: startup, the main user flows, the top routes or endpoints, heavy jobs. A project verification skill (verify-<app>) or a route table is the source when one exists; the inventory names where it came from.
  2. Measure each path with measure.py run (N ≥ 5 runs of one command, min, median, max, spread) or, for numbers another tool produced (per-endpoint latency, repeated lab traces), measure.py summarize. Web paths also get a lab trace — LCP, INP, CLS, long tasks — and the bundle size, recorded as lab data. Backends get per-endpoint latency and the query count.
  3. Estimate how fast each path should be — a back-of-the-envelope number from the work the path really needs and what the hardware or network can do — and record the basis in one sentence. The gap is measured median ÷ expected; the likely source is one of waste, cache misses, serial work that could run in parallel, waterfalls, N+1 queries, oversized payloads.
  4. Review the hot paths for wasted work: scan.py lists mechanical candidates (N+1 calls, awaits inside loops, independent awaits run one after another) with file:line; the agent reads each and checks the rest of the non-pessimization checklist (needless copies and allocations, repeated parsing or serialization, layers that do nothing, re-renders). A candidate read and confirmed is a finding at confidence 75 or above; one that is not goes to Unverified.
  5. Report — write tasks/perf/<YYYY-MM-DD>-<slug>.json in the audit schema; audit.py validate refuses a malformed one, audit.py render writes the Markdown report beside it, ranked by impact × confidence ÷ effort.
  6. File — audit.py file runs one task-registry upsert per finding (dry-run by default, --apply to write), each carrying its measurement, the expected number, file:line, the suggested fix and the measure command as its reproduction. A filed finding is later handed to Debug mode with /go "<finding> #N is slow".

Audit mode changes no product code. The lane ends at the report and the filed tasks; its Debug-only steps are kept with — skip: audit mode.

Debug mode (/perf debug <ref>)

  1. Name the slow path and one repeatable command that exercises it.
  2. Baseline: measure.py run --runs N -- <command> saved to tasks/perf/<slug>-baseline.json, before any edit.
  3. Expected: the same back-of-the-envelope estimate as Audit step 3.
  4. Hand the baseline (the reproduction) and the expected number to /debug, then /build the fix.
  5. After: the same command with the same N, saved as <slug>-after.json; measure.py compare prints the verdict and the Markdown table the PR body quotes — baseline, expected and after, one command.

A change is improved only when the after median is below the baseline's minimum, regressed when it is above the baseline's maximum, and within-noise otherwise. within-noise is never reported as an improvement.

Quality gate

/quality-gate Phase 3 (Security and Load) runs scan.py over the gate's own file list. Each candidate is a scale finding at confidence 50 until the reviewer reads the loop and the assumed load reaches it (75) — the same verification-promotion rule every phase uses.

Inputs

  • measure.py run --runs N [--warmup W] [--timeout S] -- <command ...> — the command runs without a shell; a shell pipeline is passed as bash -c '<pipeline>'.
  • measure.py summarize --unit <unit> --command '<what produced them>' <sample ...>
  • measure.py compare <baseline.json> <after.json> [--expected X] [--format json|markdown]
  • scan.py [--format json|findings] <path ...> — files or directories; .py is parsed with ast, .js .jsx .ts .tsx .mjs .cjs by a brace-tracking line scanner; other files are ignored, and node_modules, .git, dist, build, .venv and venv are skipped.
  • audit.py validate|render|file <audit.json> [--repo <root>] [--apply]

Outputs

  • measure.py run|summarize — one JSON object: command, unit, runs, warmup, samples, min, median, max, spread (max − min) and spread_pct (spread ÷ median × 100).
  • measure.py compare — verdict (improved | within-noise | regressed), both summaries, expected, and in Markdown a table with baseline, expected and after columns and the verdict.
  • scan.py — {"candidates": [{"file", "line", "pattern", "evidence", "why"}], "skipped": [{"file", "reason"}]}, sorted by file then line; the findings format prints each candidate as a four-axis line at confidence 50.
  • audit.py render — the Markdown report: Critical paths (runs, min, median, spread, expected, gap, likely source), Web vitals (lab data), Findings ranked, Unverified, Coverage gaps.
  • audit.py file — one upsert per finding, id derived under the perf namespace from the finding's file and title, kind task, labels performance plus now (impact 3) or next.

Audit schema (perf-audit/1)

{
  "schema": "perf-audit/1",
  "target": "<app or flow>", "date": "YYYY-MM-DD", "sha": "<short sha>",
  "inventory_source": "<verify skill | route table | README | none found>",
  "paths": [{
    "id": "<slug>", "name": "<human name>",
    "kind": "startup | flow | endpoint | job | web",
    "measurement": { "...": "measure.py output" },
    "expected": {"value": 5.0, "unit": "ms", "basis": "<one sentence>"},
    "source": "<likely source of the gap>",
    "lab": {"data": "lab", "backend": "<backend and version>",
            "lcp_ms": 0, "inp_ms": 0, "cls": 0.0, "long_tasks": 0, "bundle_bytes": 0}
  }],
  "findings": [{
    "title": "...", "path": "<path id>", "file": "<repo path>", "line": 1,
    "pattern": "<n-plus-one | sequential-await | await-waterfall | other>",
    "evidence": "<verbatim line>", "fix": "<suggested fix>",
    "impact": 1, "confidence": 75, "effort": 1
  }],
  "unverified": [{"file": "...", "line": 1, "reason": "..."}],
  "coverage_gaps": ["<path not measured, and what would reach it>"]
}

Edge Cases

  • --runs below 5, a summary with fewer than 5 samples, or a measurement whose samples length differs from runs → refused, exit 2: a single-run number is not a measurement.
  • A summary whose min, median or max does not match its own samples → refused by audit.py validate: hand-typed numbers are not accepted.
  • The measured command exits non-zero on any run → measure.py run exits 1 naming the run: a failing run's time is not a measurement.
  • compare on two files with different commands, units or run counts → exit 2: baseline and after must come from the same command and N.
  • A web path without a lab block, or a lab block whose data is not "lab" → refused: a single lab trace is never presented as field data.
  • A finding below confidence 75, without file/line/fix, or pointing at a path id that does not exist → refused; with --repo, a file:line that does not exist in the tree is refused.
  • A Python file that does not parse → listed under skipped with the error, never silently dropped.
  • .map(async …) callbacks run concurrently: an await inside one is not a sequential-await candidate, though a query inside it is still n-plus-one.
  • audit.py file run twice over the same report → the same derived ids are updated, never duplicated.
  • No finding verified → the report says Findings: none and nothing is filed.

Interfaces

measure.py

  • Path: .agents/skills/perf/scripts/measure.py
  • Hides: timing, warmup, the summary statistics, the minimum-run rule and the noise-band verdict.
  • Interface: measure.py run|summarize|compare … → JSON (or Markdown for compare).
  • Alternative considered: hyperfine. It is the right tool where installed, but it is not on every machine the harness runs on and its JSON shape would leak into the report schema; the skill names it as an alternative feed for summarize.
  • Depth: one call turns a command into a comparable, noise-labelled number.

scan.py

  • Path: .agents/skills/perf/scripts/scan.py
  • Hides: language detection, AST walking and brace tracking, the call-name lists.
  • Interface: scan.py [--format json|findings] <path ...>
  • Alternative considered: a prose-only checklist. It cannot be pinned by a test and drifts between reviewers; the scanner proposes, the reviewer confirms.
  • Depth: the reviewer starts from exact file:line candidates instead of reading every loop.

audit.py

  • Path: .agents/skills/perf/scripts/audit.py
  • Hides: the schema rules, the ranking formula, the report layout and the upsert argument list.
  • Interface: audit.py validate|render|file <audit.json> [--repo R] [--apply]
  • Alternative considered: the skill telling the agent to type one upsert per finding, as /sweep does. A script makes "one task per finding" a property the test suite can check.
  • Depth: one JSON file becomes a validated report and its tasks.
