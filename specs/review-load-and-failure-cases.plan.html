Five review ideas adapted from ponytail (DietrichGebert/ponytail, MIT — skills/ponytail-review, skills/ponytail-audit, skills/ponytail-debt), restated in this harness's own words and fitted to the four-axis Finding Model. The ponytail plugin itself is not installed.

¶ Summary

Reviews in this harness state the load they judged against, give every finding a concrete failure case, and read well for a human without losing the four-axis line the Apply Gate parses. The function-size rule becomes "split by job", the two shortcut-marker rules become one, and shortcut debt can be listed on demand. An A/B against ponytail's reviewer checks the result on seeded bugs.

Behavior

Expected load. Every review states the load it judged against before it reports anything: Load assumed: <who and how many run this> (source: <path | none found>). The reviewer looks for it in this order: the spec's § Edge Cases and § Decisions, the [NON-FUNCTIONAL] section of tasks/project-context.md, then the README and the deploy or routine config. If it finds none, it assumes one operator and one process, and says so. The load then drives a scale checklist: check-then-write races, the same work done by every process or session, state or lists that only grow, one query or call per item, O(n²) on input that can be large, and per-process state that has to be shared. A scale finding is valid only when the assumed load reaches it.

A failure case for every finding. Beside evidence: (where the defect is), every finding carries failure: (what goes wrong). For a correctness, security or scale finding that is the input or situation and the wrong result it produces. For a design or lean finding it is the concrete change or read the defect makes harder. A finding with no failure: line is capped at confidence 50, the same way a finding with no evidence: line is.

A human layer on top of the four axes — presentation only. A review opens with What this change does: in two or three sentences, plus the Load assumed: line. Findings are numbered across all severities, so a person reading the output, or a later turn, can refer to one by number. Each finding's description ends with what happens if it is skipped. The review closes with Verdict:, Lean: -<N> lines possible when lean findings exist, and Not checked: naming what mattered but could not be read or run. The four-axis line stays the first line of every finding, so the parsers and the Apply Gate are unchanged.

The layer adds no human-in-the-loop step. Nothing waits for an answer, nothing asks "which should I fix?", and /build still runs with no prompts between tasks. What gets applied, reported or escalated is decided exactly as today: by the Apply Gate (gated_auto at confidence 75 or higher) and by the owner axis. Verdict: restates a decision that already exists and never makes a new one. In /quality-gate it is the receipt verdict receipt.py derives (GO / HOLD / STOP). In a dispatched persona it is a summary for the orchestrator, naming the MUST-FIX numbers; the orchestrator's gate decides, not the persona.

Banned content. The reviewer personas drop the Strengths section, the persona self-description and the free-form Recommendations list. They emit no "consider…", no style taste and no vague worry: no failure: case, no finding. NITPICK stays in the enum for objective cosmetic defects (an unused import, a comment that contradicts the code).

Split by job, never by line count. The Clean Code rule in AGENTS.md and /quality-gate Phase 1.2 no longer says "functions ≤20 LOC → split". It says: split a function that does several unrelated jobs, by job; never split by line count, and never into helpers that exist only to make a function shorter. The ≤3-parameter rule stays.

One shortcut rule. A TODO(shortcut): marker that names its limit is a decision, not a finding, unless either (a) the assumed load already crosses the limit it names, or (b) the shortcut opens a hole on the never-on-the-chopping-block list (security, accessibility, trust-boundary validation, error handling that prevents data loss). In either case the shortcut itself is the finding, citing the marker and saying what it failed to account for. The rule's one home is finding-model.md § Deferrals; personas and the dispatch contract cite it instead of restating it.

Shortcut debt on demand. /wrap-up-session § Shortcut ledger stays the one home of the ledger's command and format. Its pattern also matches /* and <!-- comment prefixes. /tidy --check shortcuts runs that same ledger on demand and reports no-trigger markers as Tier 1.

Inputs

  • The diff (or tree, for /sweep and /tidy) under review, plus the dispatch payload review-dispatch-contract.md already defines.
  • The load sources named under Expected load. They are read by the reviewer; they are not a new dispatch item.
  • TODO(shortcut): markers in the tree.

Outputs

  • Reviewer and /quality-gate output in the human-and-agent format above.
  • /quality-gate Phase 3 renamed Security and Load. It records {"phase": 3, "lens": "security-scan+load", ...} in the receipt.
  • A new receipt policy hash, because finding-model.md, review-dispatch-contract.md and the gate's SKILL.md all change. Receipts minted before this change go stale once, as designed.
  • /tidy report rows for check shortcuts.
  • A Mode B /eval report comparing three reviewers on seeded-bug diffs.

Edge Cases

  • No load source anywhere → Load assumed: one operator, one process (source: none found). Scale findings that need more load than that are not emitted.
  • This harness repository → the load is several concurrent sessions sharing one clone (tasks/solutions/, the parallel-sessions learning). Races on shared registers such as tasks/todo.md are in scope.
  • Repo-survey dispatch (/sweep --routine architect) → there is no "change", so the opener is What this tree does:; everything else is unchanged.
  • Finding with evidence: but no failure: → capped at 50, reported, never auto-applied, never dropped.
  • Design finding → failure: names the change that costs more because of the defect (e.g. "adding a provider means editing A, B and C"). It is never left empty because "design has no input".
  • Marker whose limit the load already crosses → the shortcut itself is the finding, severity by impact.
  • Marker that opens a security hole → the finding is MUST-FIX whatever the marker says.
  • A TODO(shortcut): mentioned in prose without a comment prefix (this spec, AGENTS.md) → not a ledger row.
  • A descendant project with a pinned older reviewer → a finding with no failure: line reads as 50. That is the existing degrade path, not a new error.
