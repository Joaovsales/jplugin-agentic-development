¶ Summary

Claude Code cloud sandboxes reach GitHub through a proxy that accepts REST calls (gh api repos/{owner}/{repo}/..., gh api user) and refuses GitHub's GraphQL endpoint with HTTP 403. gh auth status also exits non-zero there although every REST call succeeds. The task-registry GitHub provider and the wrap-up PR path both drive gh through subcommands that use GraphQL (gh issue, gh label, gh repo view --json, gh pr), so an unattended routine stops at task-registry doctor and could never open its PR. Both move to REST: the provider calls gh api only, and the PR path runs through one script, gh_pr.py, that the wrap-up prose cites instead of gh pr. Every observable behavior stays the same; only the transport and the exact gh argv change. The decision not to miss: linked-PR exclusion in select is kept by reading each candidate's REST timeline, conservatively. The merger's post-merge check (task-registry closes) and the stranded: backstop in select read pull-request state from REST as well.

Behavior

The registry's GitHub provider speaks REST

.agents/skills/task-registry/scripts/registry/providers/github.py issues every GitHub call as gh api against user or repos/{owner}/{repo}/.... No gh issue, gh label, gh repo or gh auth invocation remains in the provider or in config.py.

  • Reachability (discover() and provider selection in config.py) is gh api user exiting 0. The failure line keeps its shape: gh is unavailable or unauthenticated — run \gh auth login\(<last stderr line>).
  • Repository resolution without a repository = line parses the GitHub remote (config.github_remote) instead of calling gh repo view; the refusal when no remote exists keeps its text, minus the gh repo view quotation.
  • Reads. list_tasks pages GET /repos/{r}/issues?state=all&per_page=100&page=N until a short page or LIST_LIMIT entries, keeping today's truncation flag and note. Entries carrying a pull_request key are pull requests, not issues, and are dropped. get_task is GET /repos/{r}/issues/{n}. The REST shape maps onto the normalized model: html_url → url, created_at and updated_at, state lower-case, labels[].name, assignees.
  • Writes send a JSON payload on stdin with gh api --method <M> <path> --input -. Create is POST /issues with title, body and labels[]; the issue URL comes from the response's html_url. Update is PATCH /issues/{n} with body and, when it changed, title, followed by POST /issues/{n}/labels only when there are labels to add. Additive labels are POST /issues/{n}/labels. Close is PATCH /issues/{n} with state: closed and state_reason completed or not_planned. Comment is POST /issues/{n}/comments. Label creation is POST /labels; label listing pages GET /labels?per_page=100 to LABEL_LIST_LIMIT with today's cap refusal. Error lines read github: \gh api <METHOD> <path>\exited N — <redacted output>.
  • A label never reaches a write unless the repository already has it. REST POST /issues silently creates unknown labels for anyone with push access, so the known-label filter is the only thing standing between an ordinary sync and a mutated vocabulary. The mock enforces it too.

Linked-PR exclusion survives without GraphQL

select still skips an issue whose fix is already under review, and still names an issue a merge left open. The provider gains linked_pr_state(task) -> Optional[Dict[str, str]] (base default None, unknown). The GitHub implementation reads GET /repos/{r}/issues/{n}/timeline (paged, capped) and looks only at cross-referenced events whose source is a pull request; an open issue that mentions the candidate counts for nothing. It answers the two keys select reads today: unresolved_linked_pr is true when any such pull request is open, in this repository or another; merged_linked_pr names the first pull request of this repository that merged with a closing keyword naming the candidate, when no pull request is open and the issue's state_reason is not reopened. The event's source.issue carries the pull request's state, pull_request.merged_at, repository_url and body, so the read costs no second call. A timeline over the cap answers None.

select evaluates the hook for the routine's candidates only, after the kind and claim filters, so a 500-issue repository costs one call per candidate rather than per issue; the stranded: backstop therefore covers the routine's own pool, and a stranded issue of another routine is named when that routine runs. A candidate whose state is unknown makes select refuse, naming the issue, exactly as the missing field does today. linked_pr_exclusion_available() answers True for this provider; the select refusal text no longer mentions a gh version. list_tasks_with_linked_prs, the per-issue closedByPullRequestsReferences and stateReason fields, the GraphQL PR_STATE_QUERY, the OPTIONAL_ISSUE_FIELDS degradation and the mock's unknown-fields knob are retired with it. routines.md states the exclusion as a timeline read and drops its gh 2.73.0 floor and its GraphQL sentence.

The post-merge check reads the pull request over REST

closing_references(pr) reads GET /repos/{r}/pulls/{n}; a pull request whose merged is false is refused naming its state, as today. The issues it closes are the closing keywords in its body — GitHub's own list (close, closes, closed, fix, fixes, fixed, resolve, resolves, resolved, an optional colon, then #N, owner/repo#N or an issue URL) — parsed by one helper that the stranded check shares. A reference outside the repository is refused naming it and nothing is closed, as today. task-registry closes then reads and closes each open issue through the REST reads and writes above.

The wrap-up PR path runs through gh_pr.py

.agents/skills/wrap-up-session/scripts/gh_pr.py (standard library plus gh api) owns every pull-request operation the wrap-up and its closure actions perform:

SubcommandREST
create --base <branch> --title <t> --body-file <f> [--draft]POST /pulls with head = current branch, draft as given; prints the PR URL
view <n or branch> --json <fields>GET /pulls/{n}, or GET /pulls?head=<owner>:<branch>&state=all for a branch; fields number,url,body,mergeable,headSha
edit <n> --body-file <f>PATCH /pulls/{n}
ready <n> [--undo]POST /pulls/{n}/ccr/ready_for_review, or POST /pulls/{n}/ccr/convert_to_draft with --undo; when that route answers 404 the proxy is absent, and the script falls back to gh pr ready [--undo] (Decision 9)
checks <n> [--watch] [--required]GET /commits/{sha}/check-runs and /commits/{sha}/status; --required reads the base branch's required checks and falls back to all when that read is refused
mergeable <n>GET /pulls/{n} .mergeable, null reported as unknown

view tells "no such pull request" (an empty list or 404) apart from "could not ask" (any other failure) in its exit code and stderr, because the terminal PR assertion depends on that distinction. The wrap-up prose (SKILL.md, closure-actions.md, routines.md, the routine-prompts README) cites these subcommands and contains no gh pr; the one-place rule for PR creation now pins gh_pr.py create exactly once.

The gh mock answers REST

tests/fixtures/task-registry/gh gains an api dispatcher over the routes above: GET user honors GH_MOCK_UNAUTH; writes honor GH_MOCK_FAIL; --input - bodies are parsed and appended to the GH_MOCK_LOG line so assertions can grep what was sent; unknown labels on any write exit 1; issues paging honors per_page and page; issue-<n>.json and issues.json keep their meaning; timeline-<n>.json answers the timeline route. The auth, issue, label and repo branches are removed, so a provider that regresses to a GraphQL-backed subcommand fails loudly.

Inputs

  • gh on PATH, able to run gh api against api.github.com: a logged-in CLI or a sandbox-provided GH_TOKEN.
  • The project's task-tracking configuration, unchanged.
  • For the PR path: the current branch, its base branch, and a PR body file.

Outputs

  • doctor reports reachable: yes — gh authenticated for <owner>/<repo> in the cloud sandbox, and every registry read and write succeeds there.
  • select reports how many candidates had their linked-PR state checked and prints a stranded: line for each candidate a merge left open.
  • gh_pr.py prints the same facts the prose previously read from gh pr (URL, number, body, mergeable, check results) in the same places.
  • Documentation states the environment requirement as "gh api user succeeds", not "gh auth status succeeds".

Edge Cases

  • gh api user fails: the provider is unreachable with the existing message; reads degrade to local-only and writes become local-pending, as today.
  • The issues endpoint returns pull requests: dropped before normalization; a fixture entry with a pull_request key proves it.
  • A page comes back exactly full at LIST_LIMIT: result_truncated is set and select refuses, as today.
  • update_task patches the body and then fails to add labels: the error names the body as already written, so a retry does not re-apply a stale body.
  • An unknown label is requested: filtered before the write, reported in a note; the mock exits 1 if one slips through.
  • A candidate's timeline exceeds the page cap: state unknown, select refuses and names the issue.
  • An open PR merely mentions the issue without closing it: it still excludes the issue. Over-exclusion is the chosen side of the error.
  • A cross-reference comes from an issue, not a pull request, in this or another repository: ignored.
  • A merged PR mentions the issue without a closing keyword: it excludes nothing and strands nothing.
  • A merged PR closes the issue in a form the keyword parser misses: no stranded: line, and the issue stays a candidate (R6).
  • closes on a PR whose body names owner/other#N: refused naming it, nothing closed, as today.
  • gh_pr.py view <branch> on a branch with no PR: exit 1 and no pull request for <branch>; a network or auth failure exits 2 with gh's stderr, so the terminal assertion reports UNKNOWN rather than "no PR".
  • Required-checks read refused or Branch not protected (404): checks --required watches all checks and says so.
  • ready outside a sandbox: the ccr route answers 404, and the script runs gh pr ready [--undo] instead, reporting which path it took.
  • mergeable is null right after a push: reported as unknown and re-queried up to three times, as the closure action does today.
  • REST writes are refused by the sandbox proxy (R3, Q1): the registry reports the HTTP status in its error line and the write becomes local-pending.
  • Windows: the Python-called mock is unreachable from the registry (#129); the mock-backed assertions are proven on Linux CI, as before.
