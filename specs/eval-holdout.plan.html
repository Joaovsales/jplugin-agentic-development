¶ Summary

/eval Mode B (variant lift) splits its prompts into a tuning set and a holdout set the variant is never tuned on, and promotes a variant only when its holdout mean beats both the unchanged skill and the variant's previous version. One script, variant-holdout.py, owns the split rule, the refusal below four distinct prompts, the manifest that pins the split before tuning and the verdict, so tuning prompts cannot become holdout prompts when scores are submitted. Prior art: mitkox/esf @ e5567fb, tools/brief_lab/README.md.

Behavior

Before any candidate is spawned, variant-holdout.py split <prompts.json> --manifest <manifest.json> reads the run's prompts, refuses a set with fewer than four distinct prompts, prints which prompts are tuning and which are holdout, and writes that membership to the manifest, refusing to overwrite one. The author tunes the variant against the tuning prompts only.

After the runs are graded, variant-holdout.py verdict <manifest.json> <scores.jsonl> reads the manifest, re-applies the split rule to its prompts and refuses it unless the rule reproduces its membership; it then reads one score per run and refuses any scored prompt the manifest lacks and any manifest prompt with no scored runs. The cut depends on the whole set, so adding or dropping a prompt after tuning can move it, and either can put a tuned-on prompt in the holdout. It then prints a report: the split, each arm's mean on the tuning set and on the holdout set, each arm's cost, and one Verdict: line. The verdict is promote only when the candidate's holdout mean is strictly greater than both the unchanged and the previous holdout means; otherwise it is reject, naming the baseline it did not beat. A variant that wins on the tuning set and not on the holdout is rejected, and the report shows the tuning win beside the holdout loss.

The three arms are:

  • unchanged — the skill as it is on the default branch, what ships if nothing is promoted (esf's "direct use").
  • previous — the variant before this tuning round (esf's "unoptimised brief").
  • candidate — the tuned variant (esf's "optimised brief").

Inputs

  • prompts.json — a JSON array of prompt strings, the organic prompts the run hands candidates.
  • manifest.json — {"tuning": [<prompt>...], "holdout": [<prompt>...]}, the normalised split split --manifest wrote before tuning.
  • scores.jsonl — one JSON object per graded run: {"prompt": <string>, "arm": "unchanged"|"previous"|"candidate", "score": <finite number>, "cost_usd": <nonnegative number, optional>}. Several runs of one prompt and arm are averaged per prompt first, so every prompt weighs the same in its set's mean.
  • --json on verdict prints the same result as JSON.

Outputs

  • split prints tuning: and holdout: lists, one prompt per line, writes the manifest when --manifest is given, and exits 0.
  • verdict prints the split, a table of arm × tuning mean × holdout mean × cost, and Verdict: promote — … or Verdict: reject — …; it exits 0 on either verdict.
  • Any refusal prints variant-holdout: <reason> on stderr and exits 2.

Edge Cases

  • Fewer than four distinct prompts (after whitespace is collapsed and ends are trimmed, so two copies of one prompt count once) — refused, exit 2, before any split is printed.
  • A prompt missing one of the three arms in scores.jsonl — refused: a baseline the report cannot show is not a comparison.
  • An unknown arm name, a non-numeric or non-finite score, a negative cost, or a line that is not a JSON object — refused with the line number.
  • A run without cost_usd — that arm's cost prints unknown, never 0.
  • A tie between the candidate and a baseline on the holdout — reject: the candidate has to beat both baselines, not match them.
  • A scored prompt not in the manifest (added after tuning), or a manifest prompt with no scored runs (dropped after tuning) — refused before any mean is computed: either moves the n // 2 boundary.
  • A manifest whose membership the split rule does not reproduce (edited by hand) — refused. An existing manifest is never overwritten by split.

Interfaces

variant-holdout.py

  • Path: .agents/skills/eval/scripts/variant-holdout.py
  • Hides: prompt normalisation, the split rule (the prompts sorted by the SHA-256 of their normalised text; the first n // 2 are holdout), per-prompt averaging and the two-baseline rule.
  • Interface: variant-holdout.py split <prompts.json> [--manifest <manifest.json>] · variant-holdout.py verdict <manifest.json> <scores.jsonl> [--json]
  • Alternative considered: a split field written into each score record by the author. It lost because a declared split can be edited after the scores are seen. Recomputing the split from the scored prompts alone lost too: the cut depends on the set, so a prompt added or dropped after tuning moves it (PR #449 review). The manifest pins the set; the rule validates the manifest.
  • Depth: one call refuses an undersized or incomplete run, reproduces the split and applies the promotion rule, so the reader of the report never re-derives which prompts were held out.

Decisions

◆DecisionD1settled

Who chooses the holdout?

Decision: A deterministic rule over the original normalized prompt set (SHA-256 order, first n // 2 held out), pinned by split --manifest and revalidated by verdict.

Options and rationale
Why
Unattended run; an author-chosen split can be chosen on the outcome, the failure the issue names.

◆DecisionD2settled

What are "no change" and "previous version" in a harness that cannot ablate a skill?

Decision: unchanged is the default-branch skill; previous is the variant before this tuning round.

Options and rationale
Why
Mirrors esf's direct use / unoptimised / optimised triple without claiming a presence/absence ablation, which SKILL.md says is not measurable here.

Exit code on reject?
